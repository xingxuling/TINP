# TINP 的三个现实例子

这些例子用来说明 TINP 在真实系统里会处在什么位置。

它们是**业务映射示例**，不是已经完成部署的客户案例。

## 例子 1：公司内部的 Agent 网络

一家公司有几个 Agent 和内部服务：

```text
员工入口
   |
   v
Agent A ---- CRM
   |
   +------ 文件服务
   |
   +------ Agent B
```

真正难的问题不是“HTTP 能不能通”，而是：

- 这次请求是谁发起的；
- Agent A 有没有权访问 CRM；
- 这份权限什么时候过期；
- 最后在哪个节点执行；
- 结果能不能追溯。

TINP 的身份、租约、会话、Provider 和回执机制，就是在验证这类问题能不能形成闭环。

当前适合作为企业内部试点或原型，不应把本机候选直接当成生产零信任平台。

## 例子 2：工厂内网里的边缘服务

假设一套本地系统平时通过：

```text
控制终端 -> 边缘节点 B -> 本地服务 C
```

如果 B 掉线，但还有备用节点 D：

```text
控制终端 -> 边缘节点 D -> 本地服务 C
```

系统希望做到的不是“任何时候都强行继续”，而是：

```text
确认原身份
确认权限仍有效
确认备用路径合法
再继续
```

如果服务 C 也不可用，则保留当前请求状态和证据，等待恢复或人工处理。

这类需求在工厂、实验室、私有网络和边缘环境里都存在。

当前 TINP 的相关证据主要来自本机多进程、TCP/TLS loopback 和恢复测试，还不能当成真实工厂部署证明。

## 例子 3：需要人工批准的高影响自动化

一个 Agent 可以自动整理数据，但“正式提交”必须有人批准。

可以把流程设计成：

```text
Agent 生成请求
   ↓
形成明确 challenge
   ↓
外部操作员签署
   ↓
验证签章、权限和请求根
   ↓
继续执行
   ↓
记录回执
```

这里最重要的不是多一个“确认按钮”，而是让批准和具体请求绑定。

普通的：

```text
confirmed = true
```

不能自动等价于独立操作员授权。

TINP 当前已经有外部操作员签章候选路径，但还没有完成生产级人员身份注册、HSM 托管和组织级密钥生命周期。

## 三个例子的共同点

TINP 最适合处理的不是“怎么发一个请求”，而是请求周围这些状态：

```text
主体
权限
会话
路径
Provider
失败
恢复
证据
```

当 Agent、服务和设备数量越来越多，这些东西会比单次 API 调用本身更难管理。

## 当前边界

这些例子展示的是 TINP 的目标位置和现有机制如何映射到业务问题。

当前仓库仍然是：

```text
VERIFIED_LOCAL_CANDIDATE / NOT_DEPLOYED
```

真实部署前仍需要跨设备验证、生产 Authority、密钥托管、可信时间和独立安全评估。
