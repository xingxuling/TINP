# 执行前约束与执行后核对

## 为什么不是从源头禁止？

**在线执行链就是先禁止不合权限的业务调用，再执行通过检查的请求。** “复核”不是先放行后追责，而是核对返回的结果是否对应原来的请求。

例如，一次读取请求即使已经获准，返回途中仍可能丢失、被替换，或者拿到另一条请求的回执。前置授权回答“可以做吗”，后置核对回答“收到的是这次请求的结果吗”。后置核对失败不能倒退时间、撤销已发生的动作。

这里的“合法”指符合配置的身份、权限、契约与策略，不是自动判断现实法律合规。

## 哪部分在常态执行路径里？

| 部分 | 职责 | 当前实现 |
|---|---|---|
| 前置强制约束 | 未通过检查，不进入业务计算 | 执行节点的 `execute()` 与 RCL 准入规则 |
| 传输与执行 | 传递请求、选择路径、执行业务、处理故障 | 节点、传输、路由与协调器 |
| 结果核对与证据 | 验证签名、绑定、结果及恢复依据 | 调用端 `verifyReceipt()`、账本与恢复模块 |
| 独立离线校验工具 | 检查已经产生的回执或文件 | OPP 结果验收等独立入口 |

这是现有职责的划分，不是新增三套服务。在线准入处于常态执行路径；独立离线校验可以在该路径外使用。不能把后者单独接在业务函数后面，就声称原业务已获得前置保护。

当前 `sdk/v1.mjs` 同时导出有界只读访问和离线验证入口。必须按具体入口判断保障范围，不能根据工具包名字推断所有函数都有相同执行约束。

## 准入具体发生在哪里？

以当前三节点 `INTENT`（执行请求）入口为例：

1. `src/suite.mjs` 准备请求、租约和会话，并选择节点与路径。
2. `src/node-process.mjs` 的转发逻辑检查信封、跳数和路径等；到达目标节点后，`onOperation()` 把执行请求交给串行执行入口。
3. `execute()` 检查租约与会话签名、主体和路径绑定、权限范围、有效期上界、输入、契约、服务状态等。
4. `evaluateRouteAdmissionGuard()` 与 `evaluateTransactionGuard()` 调用 `rcl/route.rcl`、`rcl/transaction.rcl`。结果不允许就抛出拒绝，不进入后面的业务计算。
5. 通过准入后再检查重复请求、已使用证据锚和缓存容量，最后才计算结果、生成回执并保存执行记录。

调用端说“检查过”不够。最终执行节点还要检查；切换到备用节点也不会跳过它的准入入口。网络收包、协商和转发不等于已经允许执行业务动作。

RCL 规则负责准入判断，服务端适配层提供从已验证上下文提取的事实。客户端不能直接提交一个 `allowed: true`（允许）来替代规则计算。

## 执行后究竟能核对什么？

`src/suite.mjs` 的 `verifyReceipt()` 检查回执签名，以及请求、主体、会话、能力契约、租约、输入、结果和路由等绑定。当前字符计数示例还会独立计算预期结果，不能把这项能力外推为任意业务的正确性证明。

需要分清三件事：

- **完整性和来源**：在信任指定密钥及签名实现的前提下，核对这份回执是否由相应密钥签署、内容是否变化。
- **对应关系**：核对收到的回执和结果是否属于本次请求，而不是另一个输入、会话或租约。
- **业务正确性**：仍需要该业务自己的验收条件。签名不能证明签署方没有撒谎；哈希链不能单独证明外部数据库、付款或物理设备真的发生了所声明的变化。

`src/opp-native-interop.mjs` 验收的是已有 OPP 结果，并生成 `authorityGranted: false`（未授予权限）的绑定。它不在原始 OPP 执行之前拦截，不追认权限，也不把历史回执变成下一次调用的许可。

历史证据可以成为后续准入和恢复的输入。因此，职责分开不等于把所有证据写入移到异步旁路；当前需要在回复前完成的持久化，仍应保留在相应路径中。

## 超时、未决和重试

“没有收到结果”不等于“没有执行”。当前只读纯计算路径允许在特定传输超时后重送同一份签名请求一次，节点使用去重缓存返回原回执。它不是任意写操作的通用重试许可。

需要区分：

| 情况 | 含义 |
|---|---|
| `deferred / NO_AUTHORIZED_PROVIDER` | 暂无满足条件的能力提供方，没有生成成功业务结果 |
| 持久 `pending` | 已发出的请求状态尚未确认，需要按恢复规则核对 |
| 回执核对失败 | 不能接受该结果；不能因此断言业务未发生或已回滚 |

## 是不是“最小内核”的必要组件？

在受控执行架构里，强制准入必须进入最小可信执行路径，不能只是可选调试步骤。**但不能由此推出整个 TINP 仓库都是最小安全内核，或者已经成为操作系统级的不可绕过边界。**

NIST 对 reference monitor（引用监控器）的设计要求包括每次访问必经、抗篡改，以及小到足以完整分析和测试。这里把它作为工程验收目标，而不是 TINP 已获认证的结论。

当前前置规则与执行入口已经存在；以下部署性质仍需另外证明：

- 真实资源不存在绕过入口的直连路径；调用者不能另拿数据库或设备凭据直接执行。
- 策略、密钥和执行节点代码由合适的主体控制，不能由请求者随意替换。
- 检查与实际动作之间的状态变化得到处理。长期任务或外部事务可能需要再次检查、事务或隔离，不能仅凭开始时通过一次检查就保证全程有效。
- 受信任部分足够小、边界明确，并经过部署条件下的独立评估。

HSM（硬件安全模块）可以是密钥保护方案之一，但有没有 HSM 与业务入口能不能被绕过，并不是同一个问题。

## 可以直接运行的证据

```bash
node --test --test-concurrency=1 tests/enforcement-evidence.test.mjs
node --test --test-concurrency=1 tests/conformance.test.mjs tests/profiles.test.mjs
```

新增测试专门对应这次疑问：

| 测试 | 验收条件 |
|---|---|
| 绕过调用端预检，直接向 C 和 B 送缺失租约、越权范围及扩权会话 | 执行端拒绝；所有节点的业务执行次数与回执缓存不增加 |
| 请求准备完成后撤销权限 | 执行端拒绝，业务执行次数仍为零 |
| 已执行并缓存的请求在撤销后再次进入执行入口 | 仍拒绝，不因有缓存而跳过当前准入 |
| 合法执行后篡改回执 | 核对拒收；不重新执行，也不假装已回滚 |

同一节点还有合法请求正向对照，避免“拒绝所有请求”的假通过。测试使用真实本机进程、TCP 回环传输和现有 RCL 规则，不模拟授权结论。

已有 `tests/conformance.test.mjs` 还覆盖签名、契约、有效期、重放、路由约束和证据篡改；`tests/profiles.test.mjs` 覆盖节点、路径和能力提供方故障。这些测试不等于真实业务副作用、操作系统隔离或公网部署认证。
