# TINP 使用场景

这份文档用具体问题解释 TINP 适合做什么。

TINP 不是“另一套 API”。它关注的是：**当多个 Agent、服务或节点已经能互相调用后，身份、权限、路由、故障和恢复怎么处理。**

## 1. 私有 Agent 网络

假设一家公司有几个 Agent 和内部服务：

```text
员工入口
   |
   v
Agent A ---- CRM
   |
   +------ 文件服务
   |
   +------ Agent B
```

真正麻烦的往往不是“接口能不能调用”，而是：

- 谁发起了这次请求；
- Agent A 有没有权调用 CRM；
- 权限什么时候失效；
- 请求最后在哪个节点执行；
- 结果能不能复核。

TINP 当前的身份、租约、会话和回执机制就是为这类问题做验证。

## 2. 节点或路径失效后的继续运行

正常路径可能是：

```text
A -> B -> C
```

如果 B 失效，而系统知道一条合法备用路径：

```text
A -> D -> C
```

TINP 可以在保持原有身份和权限边界的前提下尝试切换路径。

如果 C 不可用，但另一个 Provider E 提供相同契约，也可以在满足条件时换到 E。

如果没有任何可用 Provider，当前实现倾向于保留状态并进入 pending，而不是把失败包装成成功，也不会偷偷重复高影响动作。

## 3. 断线后恢复

一个任务执行到一半时进程退出、节点重启或连接中断，常见问题是：

> “我到底要不要再发一次？”

对只读计算，重复通常问题不大；对付款、删除、下单之类动作，盲目重试可能造成重复执行。

TINP 的恢复路线强调：

- 先找已有回执；
- 保留原会话和权限边界；
- 未确认的请求保持 pending；
- 不把“没有看到结果”自动解释成“没有执行”。

这也是为什么当前实现对未决请求比较保守。

## 4. 需要操作员批准的自动化

有些动作可以自动执行，有些动作必须有人批准。

TINP 当前包含外部操作员签章的候选路径，用来验证：

```text
Agent 请求
   -> 生成批准挑战
   -> 外部操作员签署
   -> 验证批准
   -> 才继续执行
```

普通的“yes / confirmed”字符串不能替代外部签章。

当前实现仍是本机候选，不等于已经完成生产级人员身份管理或硬件密钥托管。

## 5. 需要审计证据的自动化

如果系统不仅要给出结果，还需要解释：

- 谁请求的；
- 当时有什么权限；
- 走了哪条路径；
- 哪个 Provider 执行；
- 是否发生恢复或切换；
- 对应哪份回执和证据根；

TINP 的 Evidence Ledger、receipt 和恢复证据适合用来做这类实验和试点。

## 6. 边缘、本地和弱网络环境

TINP 的长期目标之一是让服务在网络条件不稳定时仍能保持有限、可审计的运行能力。

适合研究的方向包括：

- 工厂内网；
- 实验室和本地设备；
- 边缘节点；
- 私有 Agent 集群；
- 网络偶发中断的本地服务。

但当前证据主要来自本机多进程、loopback TCP/TLS 和受控恢复测试，**还不能把这些结果直接当作真实跨设备生产证明。**

## OPP 和 TINP 怎么分工

```text
OPP
负责：能力是什么、输入输出是什么、两个系统能不能接

TINP
负责：谁能调用、怎么传、失败怎么办、怎么恢复、怎么留下证据
```

两者可以一起用，也可以分别研究。

## 当前最适合的使用方式

现在更适合：

- 做私有 Agent 网络原型；
- 验证身份、权限和恢复设计；
- 做企业内部试点；
- 做需要回执和证据的受控自动化；
- 作为 OPP 能力协商之后的执行与恢复层。

当前不适合直接宣传为：

- 互联网替代品；
- 已完成公网规模验证的网络；
- 生产级零信任平台；
- 已认证的军用通信系统。
