# TINP 与常见基础设施的关系

TINP 不是用来替代 MCP、A2A、gRPC、OAuth、Temporal 或消息队列的。它关注的是这些调用真正进入执行阶段之后，**身份、权限、路由、失败恢复和证据**怎么处理。

| 技术 | 它主要解决什么 | TINP 与它的关系 |
|---|---|---|
| **MCP** | Agent 如何发现和调用工具 | MCP 解决工具接入；TINP 关注调用前后的身份、权限、路由、恢复和证据 |
| **A2A** | Agent 与 Agent 如何通信和协作 | 可以作为上层 Agent 通信方式；TINP 更关注执行治理、节点和恢复 |
| **gRPC / REST** | 服务怎么发请求、收响应 | TINP 不是 RPC 框架，可以建立在现有传输和服务接口之上 |
| **OAuth / OIDC** | 用户或应用如何授权、认证 | 生产环境可以和 TINP 一起用；TINP 不应被理解为 OAuth/OIDC 的替代品 |
| **Temporal** | 持久工作流、重试、长事务编排 | 在“恢复”上有部分问题交集，但 TINP 不是工作流引擎 |
| **Kafka / RabbitMQ** | 消息传输、缓冲、队列和消费 | TINP 不重新发明消息队列；它关注请求主体、权限、执行状态和证据 |
| **OPP** | 能力是什么、输入输出是什么、两个系统能不能接 | OPP 处理能力与互操作；TINP 接管身份、权限、路由和恢复 |

## 一句话区分

如果你的问题是：

> “Agent 怎么调用这个工具？”

先看 MCP / SDK / API。

如果你的问题变成：

> “谁在调用？有没有权限？Provider 挂了怎么办？超时后能不能安全重试？出问题后怎么证明发生了什么？”

这才进入 TINP 的问题范围。

## 不是替代，而是补层

一个更接近真实部署的组合可能是：

```text
Agent
  ↓
MCP / A2A / SDK / API
  ↓
OPP（能力与接口兼容）
  ↓
TINP（身份 / 权限 / 路由 / 恢复 / 证据）
  ↓
现有网络与服务基础设施
```

这里没有要求所有项目都必须使用全部层。TINP 的价值只在问题真的涉及这些边界时才成立。
